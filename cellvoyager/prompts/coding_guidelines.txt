Guidelines for constructing the analyses:
    1. The analyses should focus on the central disease/condition in the paper but must analyze the disease/condition in a novel way. As a result, you must ensure that the analysis has minimal overlap with both the analyses in the paper and with those already attempted.
    2. When relevant, use statistical tests to determine statistical significance. Ensure that you are printing the results of these
    3. Figures are the default, not optional: every step that yields a result MUST produce at least one printed figure (only pure QC/printout steps may skip). Prefer a plot over a text table whenever the result can be visualized. Use the sourced helpers `plot_genes_flexible(cds, genes, ncol=3)` / `feature_plot_flexible(cds, gene)` for expression, and combine multiple panels in a grid (patchwork `p1 + p2`, or `facet_wrap`). Always `print()` the final plot object so it renders inline.
    4. For analyses that depend on celltype, look at each celltype separately. Focus on the celltypes that you think will be most relevant.
    5. For suggesting novel analyses not present in the paper, focus on using new computational methods, looking at new celltypes/genes/features, and finding new ways to visualize the dataset.
    6. Each analysis should be entirely self-contained, not relying on any external analyses or datasets. It should be able to be run without changing anything.
    7. All code must be R run through monocle3, NOT Python/scanpy. Write the R code inside an IPython `%%R` cell-magic block (rpy2 is loaded via `%load_ext rpy2.ipython`); for short snippets you may instead use `rpy2.robjects.r(...)`. You can only use the following R packages: {available_packages}. DO NOT USE ANY OTHER PACKAGES.
    8. Make sure to only use data found in the Monocle3 cell_data_set object. Take advantage of as much of the metadata information as possible (colData for cell metadata, rowData/fData for gene metadata, reducedDims for embeddings, the counts/expression assays).
    9. The path to the Monocle3 cell_data_set `.RDS` file is {adata_path}
    10. The analysis should be focused on one core goal/hypothesis. It should not branch out from this significantly.
    11. DO NOT LOAD THE `.RDS` file — the Monocle3 cell_data_set is already in memory in the R global environment under the variable name `cds`. Reuse it directly across `%%R` cells (objects persist in `R_GlobalEnv`).
    12. Display all figures inline by PRINTING the ggplot/patchwork object at the top level of the `%%R` cell (e.g. `print(p)`). A computed-but-unprinted plot never appears in the notebook. Never save figures to a file.
    13. The analyses should be standard and should be analyses you think the paper missed.
    14. You have access to all previous variables/objects in the R session, so DO NOT re-load or re-compute things unless completely necessary. Remember R is 1-indexed.

Common monocle3 (via rpy2) API pitfalls to avoid:
    - The data handle is the R object `cds` (a cell_data_set), NOT a Python `adata`. Access components with R accessors: colData(cds), rowData(cds), reducedDims(cds), assay(cds, "counts") / exprs(cds), and dim(cds) which returns [genes, cells].
    - plot_cells(cds) requires reduce_dimension(cds) to have populated a UMAP embedding first. To color by cluster you must run cluster_cells(cds) first; to color by pseudotime you must run learn_graph(cds) and order_cells(cds) first.
    - cluster_cells(cds) depends on reduce_dimension(cds); learn_graph(cds) depends on cluster_cells(cds) (it uses partitions); order_cells(cds) depends on learn_graph(cds) and needs a root (root_pr_nodes or root_cells).
    - top_markers(cds, group_cells_by="...") requires the grouping column to exist in colData(cds) (e.g. clusters from cluster_cells, or an annotation column). Marker stats are returned as a data.frame, not stored on the object.
    - graph_test(cds, neighbor_graph="principal_graph") requires learn_graph(cds) first; graph_test(..., neighbor_graph="knn") requires reduce_dimension(cds).
    - Genes are addressed by rownames(cds); a human-readable symbol usually lives in rowData(cds)$gene_short_name. Subset genes/cells with R bracket syntax cds[gene_rows, cell_cols], not pandas indexing.
    - A ggplot is only rendered when the plot object is printed. At the top level of a `%%R` cell, evaluate/print the plot object (e.g. `p` or `print(p)`); assigning it to a variable without printing shows nothing.
    - For marker/DE questions prefer `top_markers(cds, group_cells_by="...", cores=1)` — it is robust and needs no model. NEVER subset cells before `top_markers()`: run it on the full `cds` and select groups via `group_cells_by` (it compares each group against the rest of the dataset, so subsetting first yields meaningless/empty markers). Reserve `fit_models()` for explicit condition contrasts and make it defensive: pre-filter genes with `filter_cds_genes(cds[, cells], num_cells_expressed_cutoff=10)`, ensure the grouping variable has >=2 levels (`droplevels(factor(...))` + `stopifnot(nlevels(...) >= 2)`), then after `coefficient_table()` inspect `unique(ct$term)`/`colnames(ct)` and never guess the term or column names (filter to `status=="OK"` and select columns via `intersect(...)`).
    - The provided CDS is already preprocessed/aligned/reduced/annotated — do NOT re-run `preprocess_cds`/`align_cds`/`reduce_dimension`/`cluster_cells`; check `reducedDimNames(cds)` and `colData(cds)` and build on what is there.
    - Curated house helpers are already sourced into the session (call them directly): `detectQC(cds)` and `filter_cds_genes(cds, num_cells_expressed_cutoff=...)` / `filter_cds_cells(cds)` for QC annotation/filtering; `get_avg_expr(cds)` for per-gene mean/median; `downsample_cds_bysample(pct, cds)` / `downsample_cds_bysample_bycluster(pct, cds)` for balanced downsampling (need a `sample`/`clusters` colData column); `get_colors(n)` for a colorblind-safe palette; and `feature_plot_flexible(cds, gene)` / `plot_genes_flexible(cds, genes)` for expression plots (the latter prints a 3-per-row grid and silently drops genes absent from the cds).
